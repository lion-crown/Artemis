# AI Agent L3 学习档案

## 目标与节奏

- 目标：在 12 周内形成 AI Agent L3 的可验证能力证据，并为 L4 的可复用框架与团队实践打基础。
- 时间投入：每天 1-2 小时，每周约 8-10 小时，累计约 100-120 小时。
- 实践载体：Artemis 项目。阅读材料与讲解默认使用中文；英文术语仅保留必要的括注。
- 交付原则：每周留下学习笔记、可运行实验或演示，以及一条可量化结论。

## 每日学习协议

每个学习日遵循以下闭环：

1. 先回答一个核心问题或完成一个小练习，不直接给标准答案。
2. 根据回答连续追问 2-4 轮：追问理由、反例、边界条件或工程实现。
3. 当天结束时整理“正确理解、待纠正点、可迁移原则”。
4. 在 1 天后、1 周后以简短问题复习同一知识点，使用间隔复习巩固记忆。

追问数量以理解质量为准：概念不清时继续追问；能正确解释原理、边界和项目对应位置时再进入下一主题。

## 代码熟悉主线（贯穿 12 周）

每天预留 20-30 分钟做代码阅读，不要求一开始读完所有源码。每次只沿一个真实请求链路阅读：
先看中文架构说明和相关测试，再看实现；最后用 3-5 句话写下“入口、核心对象、状态、输出”。

| 周次 | 阅读范围 | 应能回答的问题 |
|---|---|---|
| 1 | `docs/architecture-cn.md`、`infra/gateway/process/processor.py`、`infra/agents/manager.py` | 一条消息如何被路由到正确 Agent 并返回结果？ |
| 2 | Agent 配置、`SOUL.md`、专家与技能目录 | 系统提示词、人格、技能分别如何进入 Agent？ |
| 3 | 线程、检查点、记忆、`/compact` 和上下文用量接口 | 哪些内容会进入上下文，哪些不应进入？ |
| 4 | 工具流、轨迹、用量和异常投影 | 一次工具调用如何被记录、展示和排查？ |
| 5-6 | `business_investigation.py`、MCP 工具包装与相关测试 | Function Calling 的 schema、多轮、超时与失败降级如何实现？ |
| 7-8 | `harness-agent` 接口使用点、运行时限制和工作流相关测试 | ReAct/固定流程各在哪一层实现，循环如何被限制？ |
| 9 | 子 Agent 目录、委派文档、`TeamProcessor` 对接点 | 子 Agent 如何被委派，结果怎样回到父线程？ |
| 10 | Provider、Connector、ACP 和框架边界 | 哪些能力由 Artemis 实现，哪些由 harness 或外部框架实现？ |
| 11-12 | 选定 MVP 的完整链路和测试 | 如何从需求、实现、测试到指标形成可演示闭环？ |

代码阅读的最低验收标准：每周能讲清一个请求链路、指出 2 个核心文件、说出 1 个边界条件，并能定位至少 1 个对应测试。

## 12 周路线

| 周次 | 学习主题 | 周度验收产出 |
|---|---|---|
| 1 | Artemis 架构与 Agent 运行全链路 | 能画出“入口→调度→运行时→工具/记忆→输出”的链路图 |
| 2 | 提示词工程 | 一个有角色、约束、证据规则和输出格式的系统提示词，以及 10 条测试输入 |
| 3 | 上下文工程 | 上下文预算表；说明哪些历史、记忆、技能和工具结果应被选择性注入 |
| 4 | Harness、检查点与可观测性 | 一次工具调用的完整轨迹及其 token/耗时解释 |
| 5 | 原生 Function Calling | 一个带 JSON Schema 的小型工具 Agent，支持多轮工具调用 |
| 6 | 工具调用可靠性 | 参数校验、超时、取消、失败降级和循环上限的测试记录 |
| 7 | Agent 范式选型 | Workflow、ReAct、Plan-and-Execute、Reflection、多 Agent 的选型矩阵 |
| 8 | LangGraph 实作 | 含分支、循环、状态持久化和人工确认点的工作流 |
| 9 | 长任务与多 Agent | 主 Agent 委派两个子 Agent 并汇总结果的演示与风险复盘 |
| 10 | 框架选型答辩 | LangGraph/harness、原生 OpenAI SDK、DeepAgent 与低代码平台的对比表 |
| 11 | 业务 MVP | 真实业务场景的 PRD、范围、成功指标和可演示 MVP |
| 12 | 指标与答辩 | 准确率、耗时、成本、工具成功率、Demo 和项目复盘材料 |

## 阶段里程碑

- 第 1 月末：能够解释并实践 Prompt、Context、Harness、Function Calling。
- 第 2 月末：能够选择 Agent 范式与框架，并说明风险和工程化控制措施。
- 第 3 月末：完成一个从需求到指标的 Agent MVP，形成 L3 答辩证据包。

## 学习记录

### 第 1 周 / 第 1 天：Agent 运行链路

状态：已完成首轮回答，待通过追问巩固。

学习目标：理解用户消息从入口到最终回复的路径，以及工具结果为何必须返回模型。

已掌握：

- 能识别 `GlobalProcessor`、`AgentManager`、`HarnessAgent` 在请求链路中的核心角色。
- 能识别模型可能多轮调用工具、技能与 MCP，并最终产出结果。
- 已意识到工具调用结果要参与后续模型判断，避免模型脱离实际操作。

待巩固：

- `GlobalProcessor` 是根据 Agent 标识、会话和线程路由请求，不是按问题语义挑选 Agent。
- 工具调用次数不是固定的；可能为零，也可能有多轮。
- 检查点、轨迹、用量等在处理过程中持续记录；长期记忆可在会话结束或空闲时异步提炼。
- 上下文不是越完整越好，应注入足够、相关、可信的信息，避免成本上升和指令被稀释。

当前复习题：

1. 为什么工具执行结果必须回传模型，而不是只展示给用户？
2. 为什么不能把所有历史消息、所有记忆和所有工具结果无差别放入上下文？
3. 检查点与长期记忆各解决什么问题？

#### 追问第 1 轮：工具结果回传

回答：如果“读取文件”返回文件不存在、却不把结果回传模型，模型会误以为文件存在，
并沿着错误前提继续排查，导致后续推理越来越偏离实际情况。

评语：正确。工具结果是模型与外部真实世界之间的反馈；回传失败结果既能阻止模型基于
错误前提继续推理，也让模型有机会选择替代路径，例如搜索相近文件、询问用户或明确说明
材料不足。

### 第 1 周 / 第 2 天：提示词工程

状态：待开始。

任务：为“代码库业务规则问答 Agent”写一段 150-250 字的系统提示词，至少包含角色、任务、证据约束、输出格式和禁止事项。
